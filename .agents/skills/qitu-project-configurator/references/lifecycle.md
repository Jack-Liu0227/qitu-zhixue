# Skill lifecycle integration

Read the server-provided skillLifecycle catalog before changing curriculum, skill assignments or profile/growth purposes. Read the relevant published skills/qitu-*/SKILL.md resources through skill_read for the requested teaching method. Source methods are adapted to Qitu; never execute native OpenMAIC stage tools or DeepTutor shell snippets.

1. Inspect the actual selected template/version and its ProjectTemplateSpec. For a series use qitu-curriculum-planner, qitu-understanding-by-design, qitu-k12-core-literacy-planning and, when relevant, qitu-spiral-curriculum. Add explicit session requiredSkillIds for methods the lesson requires, alongside existing objectives, tasks, evidence/rubric and interaction requirements. Preserve frozen versions; save a new template version for changed semantics.
2. Map each session to real member slots and assistant IDs. Use the guide/inquiry/artifact role presets as recommendations, preserve existing unrelated bindings, and only select current ready/published teaching skills. Admin authoring skills are read-only configurator resources and must not be bound to student assistants. Required tools must also be explicitly authorized.
3. Use assistant.create/update with the exact provider/model pair, canonical enabledSkills and supported tools. Each responsibility has one canonical skill package; reuse its existing ID and do not create suffixed copies or duplicate assistants for a source revision. Read back each assistant. Changed package digests require review and saving a new teaching arrangement with binding.prepare, then binding.draft, binding.validate and binding.activate following the exact current operation catalog. Never rewrite historical frozen hashes to disguise a change; an old digest mismatch must remain explicit. A team reference or saved draft is not activation. Never infer phase assignments from team/member titles.
4. At runtime, the actual frozen session determines the assistant and skill pins. Teach-back, bounded support, source checking and interaction propose candidates only. Supported visuals are BoardBlock/Mermaid/KaTeX and registered optics. Questions and actions receive owner-issued stable IDs, revision scope and idempotent receipts. Preserve pending questions and private answer keys.
5. The student submits answers, observations, CER, reflections and artifact revisions through existing server contracts. Simulation, source lookup, file formatting or AI text alone is not evidence of learner mastery. Let existing learning-plan/mastery/works owners decide acceptance and official state transitions.
6. Configure dedicated profile and growth assistant IDs using the existing growth projection settings operation and exact current revision. Bind qitu-learner-profile and qitu-growth-trajectory respectively and preserve approved event routes. Candidate-only workers cannot execute interactive tools; do not bind skills with requiredToolIds to those assistants.
7. Existing Tutor completion and owner events feed the current outbox and projection pipeline. The owner verifies source ownership/hash, route/grant freshness, policy and base version before an accepted profile/trajectory appears. Never write raw student conversations, invented achievements or inferred psychological traits into projections.

Report each state separately: source package present, package published, assistant configured, teaching arrangement saved, binding active, owner-accepted evidence, projection accepted, live request verified. Expose missing tool/storage/model/knowledge capabilities explicitly. A failed or untested layer must not be reported as complete.

Fixed skill-content, file and aggregate character ceilings are removed. Declared references are loaded as versioned text and enter packageDigest. Actual model context limits still apply and must fail explicitly rather than silently truncating the skill.
