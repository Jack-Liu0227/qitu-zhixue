# ADR 0008：管理员与班主任职责边界

- 状态：**Proposed（Accepted for planning）** —— 目标规则已确定，可用于排期与信息架构评审；实现前提未满足前**不得**当作已交付能力。
- 日期：2026-09-28
- 范围：四个平台的角色职责、导航与个别学生数据访问边界（文档层面）
- 关联：产品文档 0.3 / 0.4 / 3.1 / 3.4 / 6 / 7.0 / 11.3、ADR 0002（领域边界与单一写入者）、
  ADR 0004（信息架构变更须先改文档）、`docs/PERMISSIONS.md` 第 5 节、`docs/ARCHITECTURE.md` 2.1、`docs/ISSUES.md`
- 本任务类型：**仅文档**。本 ADR 与相关文档更新**没有修改任何应用代码、数据库 schema、迁移或包契约**。

## 背景

产品文档 0.4 曾把班主任端描述为「工作台、学生管理、问题处理、数据统计、知识库、系统设置」。
这与已落地的实现和角色职责都不一致：

- 班主任端代码已经移除 `/teacher/settings`（`3b6a937 fix(teacher): remove settings route and service capability`），
  冻结的班主任业务导航只有五项：工作台、学生管理、问题处理、数据统计、知识库。
- 「系统设置」里实际上混了三类不同归属的能力：
  1. 账号与安全（凭证、MFA、设备会话、退出）——对**所有角色**成立，不应挂在班主任业务导航下；
  2. 平台与 AI 策略（模型路由、提示词、阈值）——归平台管理后台（产品文档 7.5）；
  3. 班主任自身的工作偏好——属于跨角色账户面。
- 另一方面，管理后台当前存在个别学生详情页（`/admin/students/:id`），
  而产品文档 7.6 已把「原始对话查看」列为管理员敏感行为。
  如果不明确「管理员默认看聚合、班主任做个别学生日常」，管理员很容易在实现里
  默认滑入个别学生的日常处理，绕过对象级授权与审计。

`AGENTS.md` 要求：不改变已冻结的产品导航与 UI 信息架构，除非先更新产品文档并通过评审；
涉及未成年人数据默认最小化可见范围并保留审计。本 ADR 就是这次先行的文档变更。

## 决定

1. **班主任业务导航为五项**：工作台、学生管理、问题处理、数据统计、知识库。
   **不包含「系统设置」**。`系统设置.png` 只保留为历史视觉基准，不是导航项。
2. **账号与安全是跨角色账户面**：登录凭证、MFA、设备会话、退出登录放在各端顶栏的
   账户入口，对 `student` / `parent` / `teacher` / `admin` 一致，不属于任何平台的业务导航。
3. **平台与 AI 治理设置归管理员**：模板版本、AI 策略、模型路由、审计、数据保留属于平台管理后台（产品文档 7.5 / 7.6）。
4. **管理员默认只进入聚合 / 治理视图**：不得把个别学生的日常处理流
   （学生管理、问题处理、人工干预、项目复核、班主任笔记）设为管理员默认落地页。
5. **个别学生的日常操作归班主任**：以 `mentor_assignments(status=active, mentor_user_id=自己)` 为对象级依据。
6. **管理员访问个别学生数据必须是显式动作**，并同时满足：
   - 对象级授权范围（限定到具体学生 / 资源）；
   - 最小字段可见性（只返回该目的所需字段，默认不含原始对话 / 原始语音）；
   - 目的 / 原因必填；
   - 敏感读取二次确认；
   - 写 `audit_logs`；
   - 限时有效。
7. **前端隐藏不构成授权**：入口是否渲染只是体验；后端必须对每个请求重新做对象级判定
   （产品文档 3.4、`docs/PERMISSIONS.md`）。

## 边界表

| 维度 | 班主任 `teacher` | 管理员 `admin` |
|---|---|---|
| 默认视图 | 自己名下学生的日常视图 | 聚合 / 治理视图 |
| 个别学生日常处理 | **是** | **否**（需显式授权范围） |
| 对象级依据 | `mentor_assignments(status=active)` | 平台治理范围 + 个别访问的显式范围 |
| 全局配置 | 无（不得改全局 AI 策略） | 模板、AI 策略、模型路由、审计、数据保留 |
| 账号与安全 | 跨角色账户面（顶栏账户入口） | 同左 |

## 后果

**正面**

- 班主任导航与实现一致，消除「文档说有、代码里没有」的漂移。
- 账号与安全能力不再与班级业务耦合，四个平台可以共享同一套账户面。
- 管理员个别学生访问有了明确的判定清单（范围 / 最小字段 / 原因 / 二次确认 / 审计 / 限时），
  可以直接映射为 `docs/PERMISSIONS.md` 的验收标准与后续 Issue。

**负面 / 风险**

- 这是一次**受控的冻结 IA 变更**（班主任导航去掉一项、新增跨角色账户面），
  需要产品与设计评审确认账户入口的位置与文案（见实现前提）。
- 管理员的个别学生诊断能力如果被过度收紧，可能影响平台治理排障；因此保留
  「显式授权范围 + 限时」的通道，而不是一刀切禁止。

## 实现前提（尚未满足）

本 ADR 只定规则，**以下实现均未开始**，因此状态是 Proposed / Accepted for planning：

- [ ] 跨角色账户面（凭证、MFA、设备会话、退出）尚未实现，当前也没有统一入口。
- [ ] 管理员个别学生访问的「对象级范围 / 原因 / 二次确认 / 限时」授权模型与落表尚未实现。
- [ ] `audit_logs` 业务写入尚未接入（表已建，写入为内存占位）。
- [ ] 当前 `/admin/students/:id` 只有 `requireRole(admin)` 的粗粒度校验，未按第 6 条判定。
- [ ] 产品 / 设计书面确认「账号与安全放顶栏账户入口」这一信息架构
      （班主任端代码已移除 `settings`，文档已同步）。

本次文档任务已先更新产品文档 0.3 / 0.4 / 6.1 / 7.0 / 11.3、`docs/ARCHITECTURE.md`、
`docs/PERMISSIONS.md`，并新增本 ADR；这些属于文档交付，不是实现。

在上述前提满足前，任何 PR 不得声称「管理员个别学生访问已合规」或「跨角色账户面已完成」。

## 落地步骤（后续 Issue）

1. 产品 / 设计评审确认账号与安全入口的位置、文案与四端一致性。
2. 在 API `access` 层建立「个别学生访问授权」对象：范围、原因、有效期、二次确认状态。
3. 接入 `audit_logs` 写入，并让管理端个别学生页先校验授权再返回最小字段。
4. 按 `docs/ISSUES.md` 的顺序推进 T8（管理员职责收敛）与 T7（班主任端平台设置迁移）。

## 明确不做

- 不改动应用代码、数据库 schema、迁移或包契约（本任务只改文档）。
- 不删除 `系统设置.png` 资产，也不改变冻结的产品视觉框架。
- 不因为「管理员权限更大」就允许其绕过对象级授权与审计做个别学生日常处理。
- 不把账号安全能力重新塞回班主任业务导航。

## 范围规则 (project-specific, recorded in this ADR and `docs/ISSUES.md`, no `AGENTS.md` change)

1. **No fifth client**: only four clients exist
   (`student-center`, `parent-companion`, `teacher-workspace`, `admin-console`).
   New capability must land in one of them; do not add a new app or entry point.
2. **No frozen IA change without docs/review**: same as the `AGENTS.md` baseline;
   hiding an entry in the frontend is not authorization.
3. **No score/rank/percentile/level semantics**: growth, feedback and reminders must
   not introduce scores, rankings, percentiles or level labels for students.
