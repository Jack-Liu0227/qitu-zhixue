## 4. “文件一模一样”的验收边界

建议将要求定义为：**同步范围内的相对路径集合、文件类型和原始字节 SHA-256 完全一致，远端不存在旧源码或旧文档残留。** 空目录按本地布局处理，Linux 执行权限单独校验。Windows 和 Linux 的权限、owner、mtime 不作为字节一致的替代依据。

| 类别 | 处理方式 |
| --- | --- |
| 源码、模板、工具、技能、配置示例、docs、Plan 及已审查附件 | 本地为准，逐字节镜像，含未提交及未跟踪内容 |
| `.git/`、Git reflog/index、本机 Agent 状态 | 保留各端自身状态，不复制仓库内部元数据 |
| `.env`、真实端口环境文件、认证/密钥、`/etc/qitu/` | 保持远端现有配置，不读取或输出秘密值 |
| `node_modules/`、`.next/`、`dist/`、缓存及构建日志 | 不从 Windows 拷贝；需要发布时在 Linux 按锁文件构建 |
| 数据库、uploads、`.runtime/`、`services/knowledge/` | 保留远端运行数据；不作为源码删除候选 |
| 本地 Archive、录屏、scratch、worktrees、临时输出等 | 不进入产品源码快照 |

这保证受管文件完全相同，不宣称整块工作目录包含运行数据在内完全相同。真正把目录内一切都镜像，会删除远端知识服务和运行数据，且拷贝不适用的 Windows 依赖，不应作为本次代码同步方法。

本地 `core.autocrlf=true`，远端为 `input`。本轮按原始字节传输并保留 CRLF/LF；不得借 Git checkout、编辑器格式化或文本模式传输隐式转换。1478 个换行差异中没有 `.sh` 文件；仍需在最终快照检查 shell 的 LF 和 Linux 执行权限。历史 `Plan/archive/**/snapshot/**` 已声明 `-text`，严格保留其字节和既有摘要。

## 5. 建议执行顺序

### A. 冻结来源并生成预演清单

1. 协调暂停本地和远端对受管文件的并行写入；记录 HEAD、完整 Git 状态、根路径和排除规则。
2. 从本地实际工作区创建只读快照，包含删除结果、未提交修改、新文件及本报告。检查相对路径安全、大小写碰撞、符号链接和秘密文件；禁止链接逃逸到仓库外。
3. 对快照生成 SHA-256 清单和包摘要；对远端重新生成同一口径清单。发现新增远端改动时重新计算预演，不沿用本报告数字强制覆盖。
4. 输出 `create`、`replace`、`remove`、`preserve` 四份明确路径列表。受保护目录即使本地不存在也不能进入删除列表。文件清单必须独立于构建产物。

### B. 备份和传输

1. 在 `/root/qitu-backups/sync-<时间戳>/` 保存远端所有待覆盖/移除文件、原权限和 Git 状态；验证备份摘要及可读性。备份在工作目录外，不能被同步清理。
2. 通过 SSH 将快照放入主工作树之外的独立暂存目录。使用保留原始字节的归档或二进制传输，避免 PowerShell 文本管道传递 tar 数据。
3. 校验暂存清单与冻结的本地清单相同，再执行落地。新文件先写临时文件后原子替换；共享源码及动态读取的技能/模板需安排请求排空或维护窗口，避免半更新状态被运行服务读取。
4. 只有新路径内容落地成功，才按预演列出的具体旧文件移除；逐一校验实际路径仍位于 `/root/qitu-zhixue` 内，并清理对应空目录。禁止对根目录直接使用不受控的 `rsync --delete`、`git clean` 或 `git reset --hard`。

### C. 文件一致性验收

1. 比较快照和远端：`missing=0`、`extra=0`、`type_mismatch=0`、`sha256_mismatch=0`。
2. 检查本地工作区从冻结到交付是否再次改变。发生变化时再次冻结和增量同步；否则只能声称远端等于某个旧快照，不能声称等于当前本地。
3. 两端运行文档校验、校验器回归与历史归档清单检查，确认旧计划目录消失，`docs/student/learning-plan.md` 仍存在。
4. 核对保护路径未被触碰。保存同步回执及实际统计到 `Plan/releases/` 并更新索引；回执本身也同步，随后再次比较两端受管清单。最终清单摘要放在清单外部，避免文件自包含哈希循环。

### D. 构建发布作为后续独立验收

完整源文件已相同，只说明源码同步完成。要让新业务在线生效，还需：

1. 本地先补齐并验证锁文件；按实际依赖图构建 contracts、database、ai-client 等包，再运行 API/应用类型检查与受影响行为测试。新增 company、commerce、订阅权限和用量结算必须有测试回执。
2. 在远端验证迁移账本，按发布流程备份数据库并测试迁移兼容性。不能自动运行会改变历史模板或授权的 bootstrap，也不能用模拟数据或门禁注入制造成功。
3. 安排维护窗口；对运行中的前端停止对应服务后再从 canonical 主工作树串行构建，不在正在提供服务的 `.next` 上原地重建。保留可恢复的旧构建；API 及依赖变更同时考虑实际运行的 workers。
4. 新公司端的 service、端口和 Nginx 路由作为明确发布项检查，不能因有源码就宣称已有线上入口。核验 `/api/v1/health/ready`、`dataMode=live`、数据库连接、登录、角色权限、关键订阅与学习流程及静态资源。
5. 构建过程若改写 next-env 或其他受管文件，先在本地确认并重新同步后验收；不能把新生成的源码差异留在远端。发布失败按备份恢复文件与构建；数据库回退单独按迁移兼容性处理，不能仅靠恢复源码回滚数据。
