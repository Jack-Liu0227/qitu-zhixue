# 两个模板的自然学习链路复核（2026-10-24）

## 结论与验收口径修正

此前的 [双项目逐课合成验收](20261024-live-two-projects-fullflow.md) 证明了学生提交、正式判题、教师审核、课时完成及归档的 owner 路径可走通，**没有证明零基础学生仅靠自然对话就能独立、顺畅完成课程**。脚本主动请求课件/实验、按服务端活动选择表单，并使用演示教师逐次批准质量评价。这些操作弥补了真实学习体验中的断点，不能据此宣称教学闭环已完成。

本次检查区分源码、当前冻结课程、线上返回值及浏览器行为。线上读取使用演示学生，仅对已归档的合成项目发送一次预期被拒绝的实验请求；没有注入掌握度、改写历史记录、放开门禁或操作真实学生数据。

## 门禁报错的实际复现

2026-10-24 03:55（Asia/Shanghai），线上项目 `proj-27f87104-2a45-4890-b7f0-00fb97a14322` 返回 `stage=completed`、8/8 已完成。第 3—7 课的五张历史实验卡仍返回三个可写操作；浏览器最后一张卡的“运行并比较”按钮可点击。点击得到 HTTP 409 / `TUTOR_EXPERIMENT_GATE_REQUIRED`，文案为“TheoryMastered 门禁通过后才能进入实验操作”。

这是一个已完成项目的历史卡片被错误开放操作、随后又被错误归类为未过理论门禁的问题，不能据此判断学生没有掌握理论。用户的其他具体项目仍需按项目/课时范围诊断，不能将这一复现推及所有门禁错误。

根因在 `TutorExperimentService.submit`：只允许 `practice_ready/practice_building`，将其余所有阶段统一报为 `GATE_REQUIRED`。`restore` 恢复实验图样和观察回执，却没有根据当前阶段、课时、活动及权限投影操作可用性。前端同样只读取旧卡片的 `allowedActions`。

本轮修复：

- 对作品审核、反思、发布、完成阶段返回独立的 `TUTOR_EXPERIMENT_PRACTICE_CLOSED`，说明只能回看。
- 服务端恢复历史时保留图样与真实回执，只对当前有效范围保留可写操作；不修改已持久化的历史教学消息。
- 前端在课时刷新时同步检查阶段、计划修订、课时和活动，旧卡片保持回看并说明原因，不等待重新登录才禁用。
- 正式答题卡的 `answer.theoryMastered` 是**当前课时理论目标**判定；删除“已解锁实验操作与探究任务”的越界承诺。实验仍需当前实践课及 owner 校验。

理论尚未达标时的服务端限制继续有效。课时切换、授权撤销或计划改变，不应通过修改 `project.status` 或扩大旧冻结权限修补。

## 逐课核对

“正式检查”指现有 assessment owner 可判分并写入掌握度的检查。“表达评价”指学生提交 session response 后等待当前班主任质量评价；对话中的普通回答并不自动成为该证据。

| 模板 / 课时 | 理论与展示现状 | 检查与完成现状 | 尚缺的自然衔接 |
| --- | --- | --- | --- |
| 光学 1 条纹从哪里来 | 有来源的分步板书；review/theory 均需展示回执 | 检查、反思为表达评价 | 入门现象对照和观察引导不能只靠流程图；回答后仍须到记录表单重复提交 |
| 光学 2 两列波相遇 | 三个准备概念；review 与 theory 都要求所有概念展示 | 正式检查三个概念，随后表达评价、课时确认 | 复习与新授重复覆盖；没有逐概念“演示—尝试—反馈”的连续交互 |
| 光学 3 双缝明暗 | 分步板书；实践阶段可发双缝仿真 | 表达检查 + 1 条模拟观察 + 反思评价 | 检查卡不能由现有 zero-base 工具投影自然发出；实验需要下一轮明确请求 |
| 光学 4 条纹间距 | 板书及双缝受控比较 | 表达检查 + 2 条观察 + 评价 | 观察数量不能自动证明只改一个变量；需结合实际参数检查比较质量 |
| 光学 5 单缝图样 | 板书及单缝仿真 | 表达检查 + 1 条观察 + 评价 | 现象标注、预测、解释没有统一在一个课件任务中 |
| 光学 6 缝宽变化 | 板书及单缝受控比较 | 表达检查 + 2 条观察 + 评价 | 缺少自动配对比较与按错误概念补救的课程交互 |
| 光学 7 两类现象联系 | 板书及有限宽双缝仿真 | 表达检查、观察、作品审核 | 已保存证据到 CER/作品正文仍靠学生手动组织和选择 |
| 光学 8 展示与反思 | 有分步板书，最终课仍要求 review/theory 展示 | 作品通过、回应/反思评价及归档 | 应围绕个人作品答辩；当前仍有重复新授式课件步骤 |
| 战机 1 最小游戏规则 | 普通生成板书；无教学课件实例/阅读回执 | review/theory/check/reflect 均为表达评价 | 未接入可复用课件学习区，开始即依赖教师逐活动评价 |
| 战机 2 循环与坐标 | 普通板书/代码示例 | 循环、坐标的正式检查，其余表达评价 | 缺少逐帧位置、变量变化的注册演示；课件与检查入口未统一 |
| 战机 3 按键与碰撞 | 普通板书/代码示例 | 输入、碰撞的正式检查，其余表达评价 | 缺按下/按住和矩形重叠的可操作教学组件；过本课不等于立即放开历史卡 |
| 战机 4 窗口与移动 | 普通板书；本地 Python/Pygame 实践 | 多个活动均为表达评价 | 站内没有受控代码运行及自动回执链；源码/结果靠提交说明 |
| 战机 5 子弹与敌机 | 普通板书；本地实现对象运动 | 表达、代码、测试记录及教师评价 | 没有对象生命周期可视化与测试输出直接关联的反馈 |
| 战机 6 计分、生命、重开 | 普通状态图；本地功能测试 | 表达评价 | 没有状态切换演示、具体失败用例到同目标补救的自动衔接 |
| 战机 7 测试交付 | 本地实机验证及提交作品 | 教师审核、学生发布 | 上次在验收机运行 Pygame 不等于产品已提供学生可用的运行环境 |
| 战机 8 展示反思 | 对作品解释与答辩 | 作品审核回执、反思评价、归档 | 应由实际代码、测试与版本差异驱动追问，当前主要靠文本表达 |

两模板的准备目标为 concept 类型；不能把历史 memory/procedure 的置信度次数规则解释成所有学生每个概念固定答对三次。

## 仍未打通的关键接口

1. **复习和新授重复**：光学把 review/theory 都设为 `teaching_delivery`，`projectLessonActivities` 又要求每个活动覆盖 `teachingSpec.concepts` 全集。第 2 课不是一次讲清三个概念就够，需要两组活动的展示回执。应在新模板合同明确复习范围与本轮概念，而不是让提示词绕过回执。
2. **动态展示能力不足**：`LessonCoursewareCard` 的内容只有 caption、TeX、nodes/edges 和翻页位置。它是结构化分步教学，不是相位联动、波形叠加、坐标运动或碰撞拖动的交互组件。正式定量仿真与理论示意应有清晰区分；低风险教学示意可以在理论阶段使用，不能借此放行实验写入。
3. **每课问答没有同一完成路径**：光学主要第 2 课、战机第 2/3 课接入正式 mastery 检查；其余 check 是 `session_response`。光学 zero-base 的模型 schema 当前在非 practice 状态只允许查找/复用/生成板书，排除了已登记的 `choice_question`；而板书 owner 只允许 review/theory。提示词要求“检查”，实际工具却没有对应候选路径。这是需要按活动修正的能力投影，不能只加提示语。
4. **不会时无法回看**：原 `TutorCoursewareService.read` 在 pending question 存在时清空所有课件，`position` 也拒绝翻页。本轮已改为可回看经过权限/来源核验的既有课件；继续学习仍禁止，题目不替换、不自动判错、不产生掌握度。
5. **教师成为每次活动的同步依赖**：两模板冻结的质量策略要求 `current_teacher`；普通表达、观察或反思只保存并不足以完成活动。脚本使用教师账号批准掩盖了等待。若要 AI 引导的连续课堂，应制定并发布新的课堂评价策略：客观检查由现有判题 owner 负责，有界课堂反馈与产物审核分开，教师保留需要人工判断的作品、安全、异常和复核；不能静默改变历史项目策略。
6. **自动推进依赖前端多步写入**：`TutorLessonAssessmentService.answer` 只提交判题；课时完成与项目 reconcile 分开，`CurrentLessonCard` 在完成之后额外调用 reconcile。中途失败会出现完成了某课、项目阶段未对齐的窗口。应让服务端协调器根据已提交的真实证据幂等对齐，仍复用原有三个 owner，不新增平行状态机。
7. **课件资产化覆盖不一致**：光学有实例、来源核验、候选版本及管理员审核发布路径；战机模板没有 `teachingSpec`、课件能力和对应知识库 grant，线上 context 也没有 `teachingMode`。标题“零基础”不能代替合同接入。未审核的项目候选不能直接充当跨项目发布资产。
8. **下一步需要学生猜**：看完课件仅刷新 context；完成检查后要手动继续检查/保存表达；实践卡有时要主动请求；完成课时又要选证据并申请。应由现有 owner 的当前活动和 blockers 给出一个明确的下一步，而不是再造一套前端进度。
